# Letopis / Letopis-mcp

Движок архива и поиска по Telegram-чатам (`tgarchive/`), поверх которого строится
тонкий MCP-сервер.

## Репозитории

- `origin` → https://github.com/Toligrim/letopis.git — оригинальный движок.
- `letopis-mcp` → https://github.com/Toligrim/Letopis-mcp.git — публичный форк,
  здесь строится MCP-сервер поверх движка. Основная площадка для новой работы.

Оба remote настроены в этой рабочей копии — пушить явно в нужный (`git push origin ...`
/ `git push letopis-mcp ...`), не полагаться на дефолтный.

## Правила

- **Никогда не коммитить**: `config.toml` (содержит реальные `api_id`/`api_hash`
  Telegram-приложений), `data/` (индекс + служебные ledger-данные), `archive/`,
  `*.session`, `.env`. Всё это уже в `.gitignore`. Схема конфига — в
  `config.example.toml`, его и обновлять при изменении формата настроек.
- Перед `git add` в этом репо — всегда `git status` глазами: `config.toml` и
  `data/` не должны туда попасть даже случайно (публичный репозиторий).
- Движок (`tgarchive/`) и данные разделены по дизайну (см. README, раздел
  «Устройство») — MCP-код не должен предполагать, что архив/сессии лежат в этом
  же гите.

## Оркестрация: Claude Code — только дирижёр, не исполнитель

В этом проекте (сборка MCP-сервера) роль Claude Code в чате — **оркестрация**,
не самостоятельное выполнение. Пользователь общается только с этим чатом; вся
фактическая работа (написание кода, правки, запуск команд, тесты) обязательно
делегируется в **Codex** через `mcp__codex__codex` / `mcp__codex__codex-reply`
(см. глобальный `~/.claude/CLAUDE.md`, раздел «Делегирование: сабагенты через
Codex MCP» — там же дефолтные параметры модели/sandbox/approval-policy).

Из этого следует:
- Claude Code сам не редактирует файлы `tgarchive/`, не пишет MCP-код и не
  запускает build/test-команды напрямую — эти шаги ставятся как задачи Codex.
- Роль Claude Code: держать план работы, разбивать его на шаги, формулировать
  самодостаточные промпты для Codex (Codex не видит эту переписку — контекст
  задачи нужно класть в промпт целиком), запускать их, читать результат,
  проверять на соответствие плану, при необходимости продолжать сессию через
  `codex-reply` по `threadId`, и отчитываться пользователю по-русски.
- Читать файлы/git-историю/грепать код напрямую — можно (это ознакомление,
  не выполнение работы). Изменять состояние репозитория (коммиты, правки кода,
  запуск скриптов, установка зависимостей) — только через Codex.
- Если пользователь явно попросит Claude Code сделать что-то самому в обход
  Codex — это разовое исключение, не отмена правила по умолчанию.

### Как ставить задачи Codex эффективно

- **Одна конкретная, завершаемая задача на один вызов.** Не бандлить в один
  промпт чек-лист из 5-7 разных под-исследований/под-реализаций ("прочитай
  10 файлов, построй карту из 6 разделов, проведи live-эксперимент, покритикуй
  архитектуру" — это перегружает контекст самого Codex и раздувает расход
  токенов). Если у этапа несколько независимых частей — разбивай на несколько
  вызовов `codex` / `codex-reply` подряд, каждый с узким, ясно завершаемым
  scope, и проверяй результат между ними.
- **Всегда `approval-policy: "never"`, никогда `"on-request"`.** При
  `on-request` Codex может остановиться и спросить интерактивное
  подтверждение на shell-команду — в этом headless-оркестрированном режиме
  подтвердить это некому, и вся сессия зависает (уже проверено на практике).
- **Всегда `sandbox: "danger-full-access"`, не `read-only`/`workspace-write`.**
  На хосте `shuvalova` `kernel.apparmor_restrict_unprivileged_userns=1`, а
  подходящего AppArmor-профиля для sandbox-helper'а Codex нет — из-за этого
  `read-only`/`workspace-write` (использующие bubblewrap/user namespaces)
  падают ещё до старта задачи (`bwrap: loopback: Failed RTM_NEWADDR`),
  задача уходит в фон и возвращает пустой результат. Это подтверждённый
  сбой окружения, не промпта. `danger-full-access` — это и есть дефолт в
  `~/.codex/config.toml` на этой машине; полагаться на строгие инструкции
  в промпте (не мутировать архив/сессии/конфиг, только читать нужные файлы)
  и на `.gitignore`, а не на OS-sandbox.
- Долгие вызовы уходят в фон автоматически — не нужно их обрывать; дождись
  уведомления с результатом, не дублируя вызов.
- Полное ТЗ на MCP-сервер (стадии, лимиты, контракты tools) лежит в
  `.mcp-planning/spec.md` (в `.gitignore`, не коммитится). Это основной
  референс, который Codex должен прочитать сам в начале каждой стадии —
  не нужно пересказывывать всё ТЗ в промпте, достаточно указать путь и
  конкретный подраздел/этап, который сейчас в работе.
